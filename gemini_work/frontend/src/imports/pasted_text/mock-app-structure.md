【重要：まずはバックエンドなしのモック動作として実装する】

現段階ではSupabase、FastAPI、Gemini APIなどの外部サービスには接続しないでください。

まずは「仮データだけでアプリ全体が実際に操作できる状態」を作成してください。

後からSupabaseやFastAPIに置き換えられるように、データ取得・保存処理とUIをできるだけ分離した構造にしてください。

【仮ユーザー認証】

実際のSupabase Authは使用せず、仮ログインを実装してください。

ログイン画面で以下のアカウントを入力するとログインできるようにしてください。

メールアドレス：

[demo@example.com](mailto:demo@example.com)

パスワード：

password

ログイン成功後はダッシュボードへ遷移してください。

ログアウトを押すとログイン画面へ戻るようにしてください。

認証状態は仮データで管理してください。

可能であればlocalStorageを利用して、ページをリロードしてもログイン状態が維持されるようにしてください。

【仮データによるCRUD】

実際のデータベースは使用しません。

以下の操作をすべてUI上で動作させてください。

・予定追加
・予定編集
・予定削除
・予定詳細表示
・予定一覧取得
・今日の予定取得

予定を追加するとカレンダーに即座に反映してください。

【仮AI処理】

Gemini APIには接続しないでください。

代わりに、AIが生成したように見える仮レスポンスを用意してください。

ユーザー限界測定では、回答内容に応じて複数の結果が出るようにしてください。

例えば、

高負荷タイプ：

LIMIT
87 / 100

二つ名：
「鉄人28号」

メッセージ：
「その生活をあと3日続けたら、人間ではなくなります。」

中負荷タイプ：

LIMIT
64 / 100

二つ名：
「意外と普通の人間」

メッセージ：
「無理はできる。でも無理した次の日はちゃんと死ぬタイプです。」

低負荷タイプ：

「ガラスのメンタル」

メッセージ：
「予定を2つ入れただけでHPバーが黄色になっています。」

のようにしてください。

回答によって結果が変化しているように見えることが重要です。

【仮AI総括】

「本日の総括」ボタンを押すと、今日の予定を利用して仮のAI結果を表示してください。

例えば予定が多い場合：

今日の総評：

「今日は動きすぎや！」

Next Action：

「明日はベッドから1歩も出るな。」

予定が少ない場合：

今日の総評：

「今日ほぼ寝てたやん。」

Next Action：

「明日は地球防衛するレベルで動け。」

予定が非常に多い場合：

今日の総評：

「予定表がもはや学生のものではありません。」

Next Action：

「明日の予定を3つ減らしてください。これは命令です。」

などの結果を表示してください。

単なる固定文章ではなく、今日の予定数や予定時間によって結果が変わるようにしてください。

【AI生成中の演出】

「本日の総括」を押した直後に、即座に結果を表示しないでください。

1～2秒程度の疑似的なAI処理時間を設けてください。

その間、

「今日の予定を解析中……」

↓

「あなたの体力を計算中……」

↓

「明日の地獄を予測中……」

↓

「査定完了」

のようなローディング演出を表示してください。

ユーザーから見て「AIが本当に処理している」ように感じられる演出にしてください。

【重要：後からバックエンドへ置き換えやすくする】

現在は仮データを使用しますが、コード上では以下のようなデータアクセス層を想定してください。

authService
scheduleService
userService
aiService
settingsService

例えば、

authService.login()
scheduleService.getSchedules()
scheduleService.createSchedule()
scheduleService.updateSchedule()
scheduleService.deleteSchedule()
aiService.assessLimit()
aiService.getDailyFeedback()

のような関数を通してデータを取得・保存する構造にしてください。

現段階ではこれらの関数の内部で仮データを返してください。

後から、

authService
→ Supabase Auth

scheduleService
→ Supabase Database

userService
→ Supabase Database

aiService
→ FastAPI

へ差し替えられる構造を意識してください。

UIコンポーネントから直接データ処理を行わず、できるだけデータアクセス処理を分離してください。
